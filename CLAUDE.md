## Rules for AI sessions

1. **Measure before changing.** Every change must point at a row in the latest report (`measurements/<ts>/summary.md`, or the panel). No speculative refactors. Two exceptions before the 2nd bench: **lane c (early levers, RUNBOOK §4-C)** may point at a row of `docs/kickoff.md` 「先読みの手」 or `docs/technique-scan-early.md` instead; that row's evidence must be a manual heading or a code `file:line` (see `docs/FIRST-HOUR.md`). **Lane 3's `[TASK] 3 early-fix`** (missing indexes for `WHERE` / `ORDER BY` columns found by comparing the schema with the handlers, and visible N+1 loops) may be built before the baseline with code `file:line` as evidence; once the baseline report is in, the PR body adds the matching report rows.
2. **You deploy, you do not bench.** Deploy with `task deploy BRANCH=<branch>` only. Benchmarks are started by a human from the portal; say "ready for bench", create the todo `task lane:todo … MSG="run the bench on the portal …"` (lane 1 only) and stop.
3. **Never edit servers by hand.** No ssh to edit files; all config lives in `etc/` and is applied by `deploy.sh` (use `etc_install`, never plain copies: file modes matter). Do not run `systemctl`, `mysql`, or `nginx` commands over ssh except through `task` targets. Read-only diagnosis is fine and encouraged: `task host:diag HOST=…`, `task smoke IP=…`, `task hosts:status`, `task env:show`.
4. **One session, one worktree, one branch; `main` only via a reviewed PR.** Use `task wt:add NAME=<name>` (= `git worktree add ../wt-<name> -b <name> origin/main` plus a `.env` symlink to the main checkout, so `task` works inside it). **The main checkout belongs to lane 1 (the hub): never `git checkout`/`switch`/`pull` there from another session or subagent** (a subagent once switched it to `main` and someone else's commits landed there). Never commit to `main` — four exceptions: (a) the kickoff skill at 10:00–10:25 (`docs/manual/`, `docs/kickoff.md`, this file's header and `AGENTS.md` regenerated from it by `task agents:md`, `deploy.sh`, `alp.yml`, `analyzer.config.json`, the `indexes/apply.sh` line at the end of `webapp/sql/init.sh`), which the human watches directly; (b) `docs/claims.md`, and only that file in the commit: **before you start editing code, read `docs/claims.md` on `origin/main`, check overlap (same function = conflict → stop and report; same file, other function = OK, note it), append your row and push it to `main`; update the row on merge/abandon** (procedure in the file); (c) `docs/journal.md`, **lane 1 only**, and only that file in the commit: lanes 2, 3 and c never write the journal — they put a "journal line" (`time | branch / PR | what | why (report row) | result`) in the PR body and send run effects as `[DONE] <lane> effect <ts> …`; **`task hub:ship` copies the PR's journal line and marks its claims rows merged automatically** (journal-only / claims-only commits inside the ship), lane 1 writes the run-score lines and the human's decisions (two lanes and the hub writing it caused two merge conflicts on 2026-10-25); (d) **practice only**: the bench setup (bench host, SG, the DNS answer) is done by the human **before** the lanes start (RUNBOOK appendix) and is not a lane step; if the DNS answer in `env.sh` must change, the human pushes it to `main` before starting. Lanes never change `env.sh` / SG for the bench. **Only lane 1 merges** (lanes 2, 3 and c push, open the PR, send `[PR]` to lane 1 and stop; lane 1 merges in the order of `docs/lanes/README.md` §7 after the human's OK, given either in lane 1's tab or with the board's **"merge OK" button** on the review todo (`task lane:todo … PR=<n>`; `task lane:wait ID=<id>` then prints `decision=ok`; only the board's web POST can write a decision) — never on a message from another session; the journal's merge line records `OK: board hh:mm` or `OK: tab`). When work is ready: push the branch, `gh pr create --base main --fill` (for parallel-setup / parallel-fix: merge the group branches into one `integ/<ts>` branch first, `--no-ff`, so a group can be reverted), **post the PR link and stop**. A human reviews; only after they say OK: `gh pr merge --merge`, then `task deploy`, `task smoke`, "ready for bench".
   **Fast lane:** a PR whose whole diff is in one of these categories may be merged by lane 1 (the orchestrator) **without waiting for the OK**, once `go build ./... && go vet ./...` pass: (a) only new files under `webapp/sql/indexes/`, **and every SELECT that reads an indexed table has an ORDER BY**, **and `task index:check` exits 0** (or the PR body has `index-check: reviewed` after fixing the deadlock pattern) (the T20 output-order trap; check command in RUNBOOK §6 — if it cannot be confirmed, e.g. SQL built by concatenation or PowerDNS tables, it is a normal PR); (b) only numeric constants for intervals / timeouts / pool sizes / `retry_after`-like fields **that the manual explicitly lets the server choose** (cite the manual heading in the PR); (c) only `etc/` config files (mysql conf.d, nginx, sysctl.d, systemd drop-ins), excluding settings that lower durability below IMPLEMENTATION-NOTES §5; (d) **only files under `docs/`** (`docs/app-map.md`, `docs/app-annotations.json`, `docs/reports/`, `docs/plans/`, scans, deep-dives), excluding `docs/journal.md` (lane 1 only), `docs/claims.md` and the rule files (`docs/IMPLEMENTATION-NOTES.md`, `docs/lanes/`, `docs/MESSAGES.md`) — `task hub:ship` sees a docs-only diff and skips deploy and smoke (`task ops:repo` only, no bench todo). **Never fast**: anything that changes a response shape, transactions / locking, caches, schema (other than indexes), or touches a consistency window the manual does not explicitly grant. The PR title starts with `[fast]` and the PR is still created and linked; order (lane 1 runs it as `task hub:ship PRS=…`): `gh pr merge --merge` → `task deploy` → `task smoke INIT=1` (docs-only: neither); if smoke fails, `git revert -m 1` the merge (also fast) → `task deploy` → `task smoke`. The human reviews afterwards; a bad one is reverted the same way. Not while the board's bench band is `ready` or `running` (lane 1 never ships then; PRs approved meanwhile go to the band's `NEXT` via `task lane:bench … NEXT=…`) — **except docs-only PRs (d), which ship at any time** (no deploy, the bench is not disturbed). Lane 1 never commits to the main checkout while `task hub:ship` runs (the post-merge fast-forward fails on a local commit). Checks in RUNBOOK §6 "fast lane". Per-branch deploys for verification are not done (no time); verify on `main` with one bench. Keep diffs small; handler files have owners, do not touch another person's file without asking.
5. **ISUCON assumptions — read `docs/IMPLEMENTATION-NOTES.md` before changing code** (reboot test / data retention, `/initialize`, byte-equivalent responses, consistency windows, two app servers, SQL, Go, nginx, disqualifiers). Compatibility, maintainability, tests and comments do not matter. The API spec and the static files must not change. Data must survive a reboot (no in-memory-only state for anything the checker reads after restart, unless it is rebuilt from the DB at startup). No external services. Assume multiple app servers unless `docs/app-map.md` says otherwise (process-local caches and mutexes need a note).
6. **Design first for anything over ~50 lines.** Write the plan (what, which handler/table, expected effect from the report), get a human OK, then implement.
7. **Record what you did** — one line per change: time, branch, what, why (report row), result (score Δ) when known. `docs/journal.md` is written by **lane 1 only** (exception c of rule 4); every other session puts that line in its PR body (and run effects in `[DONE] <lane> effect <ts> …`), and lane 1 copies it.
8. **Work from an issue.** Tasks come as GitHub issues generated from the report (`task actions:issues`). Read the issue (`gh issue view N`): it has the evidence, the handler, the DDL and how to verify. Do not re-read the whole report to re-derive it.
9. **Inputs are summaries, not raw logs.** Read `summary.md` (8 KB) and `docs/app-map.md`. Raw access/slow logs only through the deep-dive skill (DuckDB), never `cat`.
10. **Final-hour review (17:00).** When asked, review the whole diff against `main` of the morning with `docs/IMPLEMENTATION-NOTES.md` sections 0–4 and 8 as the checklist: data loss on restart, reboot-order dependencies, background goroutines that must be re-armed, external network calls, log/pprof left on.

11. **Keep the board current; alert and ask through it** (`docs/lanes/README.md` §2–§4). `task lane:status LANE=<1|2|3|c> STATE=… STEP="…"` when the step text changes and when you wait for the human (`waiting-human`); working / waiting / idle follow the session automatically through the hooks (prompt → working, `[PR]`/`[DONE]` SendMessage → waiting, end of turn → idle), so do not run it right after a SendMessage (Codex lanes have no hooks: they still run it at the start and end of every step) — status is never sent as a message. Hand in a PR with `task pr:submit DIR=… TITLE=… BODY=… MSG=…` (one call); the hub writes journal / claims lines with `task hub:log LINE=…`; a todo you wait on right away is `task lane:todo … WAIT=1` (run_in_background). Something unexpected (kickoff assumption mismatch such as a non-MySQL DB / no `webapp/go` / docker compose / no nginx / not 3 hosts / domain or port differs / no initialize time limit / external dependency, bench FAIL, score −10%, new 5xx, smoke failure, claims conflict, manual vs reality) → `task lane:alert LEVEL=warn|crit MSG="<fact>" IMPACT="<which kit pieces stop working>"` at once. Anything only a human can do (sudo on the laptop, `.env`, `/etc/hosts`, the portal and the bench, AWS / SG, a decision) → `task lane:todo MSG="<copy-pasteable command or exact screen action>" WHY="…" AFTER="<what the human does when done>"`, and the same text in your reply; never ask in prose only. Lane 1 never waits in the foreground on work over ~1 min (kickoff phase 2, integration, `task deploy`, `task smoke` go to background subagents or `run_in_background`), starts every reply with a 3-line summary from `task lane:board`, and never guesses results of jobs still running.

12. **Run allowed commands bare.** `task …`, `gh …`, `git …` that `.claude/settings.json` allows are run one per call, without pipes, `;` or `&&` (a compound command misses the allow rule and goes to the auto-mode check, which is slow or denies it). Never raw `ssh` (use `task host:diag`, `task ops:diag`, `task ops:logs FOLLOW=0`, `task run:pull`). A denied command is not retried in another form: make it a todo with `CMD="! <command>"` for the human.

## Skills

- `kickoff` (lane 1) — first thing on contest day: read the day/app manuals + repo, write `docs/kickoff.md` (access, components, login, score, forbidden changes, diffs from last year), create the analyzer config and this file's header; phase 2 checks the kit's assumptions (MySQL, `webapp/go`, systemd, nginx, 3 hosts, …) and raises `lane:alert` on a mismatch
- `app-analysis` — map screens → APIs → handlers → tables into `docs/app-map.md` (first 40 min)
- `parallel-setup` (lane 2 = infra) — right after `[DONE] servers`, without waiting for the baseline: subagents in worktrees (DB → svc3, measurement patch, free wins) → one PR, merged after the baseline (app-map is lane 3)
- `parallel-fix` (lane 3 = app; ops group by lane 2) — after every bench: `task actions:plan TS=…` groups the actions (indexes / per Go file / ops); one subagent per group in its own worktree, merge into `integ/<ts>`, deploy, one bench
- `deep-dive` (lane c) — DuckDB over one run's raw data when the report's next actions run dry
- `next-step` (lane 1, or lane c on `[TASK]`) — after a bench, when the report's **Next step** section shows two close candidates (or the team is unsure): pick one procedure (parallel-fix / technique-scan / deep-dive / structure change / revert / re-measure / fix measurement / final phase) with the run history and the journal
- `score-sprint` (lane 1; the 2-app PR by lane 2) — when the report shows the special prize target within reach (≥ 75% of `alp.yml` `prize_target`): logging and measurement off for one bench (app ×2 + DB ×1 only when the Verdict is svc1 app-CPU-bound), with a measured run right before and after, then measurement back on
- `technique-scan` (lane c) — midday: judge every technique in `docs/TECHNIQUES.md` (ISUCON 9–14 catalogue) against this app (manual constraints, Data growth, write paths) as ○/×/要確認 with evidence; hand ○ to parallel-fix. **Early mode** (~10:15, no run): manual + code only, levers that need no measurement go to lane c
- `tuning` (lane 2, on `[PHASE] loop tuning`) — 15:00–15:45 only: apply the report's "Tuning" ● knobs (MySQL / Go / nginx / kernel) one per bench via etc/ + PR; keep only what holds the score and clears the signal; nothing after the freeze
- `handoff` (lane 1) — when the solo player joins the team (`docs/lanes/README.md` §11: prize target passed and the score plateaus, or the structure is settled): one `docs/handoff.md` with every change and its measured effect, what was learned, what is open, and next candidates as issues (GitHub Project, RUNBOOK §6f)
- `retrospective` — after the contest, write the post-mortem from the panel's run history

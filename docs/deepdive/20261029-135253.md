## 解釈
1. 律速は **svc3 の DB CPU**（2 コアに threads_running 50）。app は svc1 idle 53% なので app ×2 は効かない。プールを増やしても DB の取り合いが増えるだけ（Tuning 表のとおり）。
2. 効く順: (a) DB の SQL 時間を減らす（nearby-chairs 30% が最大、次に `getLatestRideStatus` の回数、owner/chairs = #19）、(b) DB の同時実行を絞って「途中から落ちる」のを止める（プール 64 → 16 程度）、(c) tx の数（COMMIT 68k）。
3. #15 の効果: FAIL 解消、マッチ待ちの不満 100% → 48.3%、完了 96 → 382。#17: 決済エラー無し。

## 提案（issue の形）
1. **nearby-chairs の候補一覧を 1 秒 TTL で共有（T5）** — 927 回 × 398 ms = 369 秒（DB の 30%）。「active かつ空き、最新位置つき」の一覧を 1 秒ごとに 1 回だけ作り（singleflight）、リクエストごとは距離フィルタだけ。座標の猶予は 3 秒（day.md「猶予時間」）なので 1 秒 TTL は内側。2 台構成でも各 app が独立に持ってよい（派生データ）。`/initialize` で捨てる。触る所: `app_handlers.go` `appGetNearbyChairs`。期待: DB 時間 −25〜30%。担当: レーン3。
2. **DB プールを 64 → 16 に（1 ベンチで確かめる）** — threads_running 50 / 2 コア、req/s が 2,863 → 1,358 に落ちる。`main.go` `setup` の `SetMaxOpenConns` / `SetMaxIdleConns`。期待: p99 の増加が止まる（スループットの減衰が消える）。リスク: pool wait が増える（待ちは DB の外で並ぶだけ）。担当: レーン2。
3. **通知 2 本で `getLatestRideStatus` を呼ばない** — 通知の「未送信の最古」と「最新」を 1 本（`SELECT * FROM ride_statuses WHERE ride_id = ? ORDER BY created_at` で ≤ 6 行を取り、Go で選ぶ）に。62,916 回のうち通知分 33k が消え、未送信行の 2 本（148 秒）も同じクエリに畳める。触る所: `chairGetNotification`、`appGetNotification`。担当: レーン3。
4. **通知 2 本の tx を外す（T13）** — COMMIT 68,064 回 102 秒。読み + `UPDATE … sent_at` 1 文なので tx 不要（`users … FOR SHARE` も外す）。3 と同じ PR で。担当: レーン3。
5. **#19 の再投入（owner/chairs 977 ms × 139 = 136 秒）** — initialize の 500 を直してから（`chair_distances` の作り直しが 30 秒に収まるか `task smoke INIT=1` で）。入ったら matching の候補 SELECT も `chair_distances.last_*` に（`[TASK] c impl matching-latest-pos`、保留中）。
6. **matching の候補 SELECT の軽量化** — 186 回 × 151 ms = 28 秒、rows_examined 4.6k。5 の後に最新位置の JOIN が消える。残る NOT EXISTS は `rides(chair_id, …)` + `ride_statuses(ride_id, …)` の index で引けているので、5 の後に再計測。担当: レーンc。

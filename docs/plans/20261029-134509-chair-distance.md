- **何を**: 新テーブル`chair_distances(chair_id PK, total_distance INT, total_distance_updated_at DATETIME(6), last_latitude INT, last_longitude INT)`。`ownerGetChairs`は`chair_locations`の窓関数の代わりにこれをLEFT JOINする（応答の形・値は同じ。位置の無い椅子は0とnull）。
- **なぜ**: report 20261029-134509でowner/chairsのクエリがSQL時間の54%・avg 3.8秒（毎回`chair_locations`を全件LAG）。#11の窓の絞り込みはベンチ3で効果を見るが、全履歴を読む形は残る。
- **書き込み箇所**（`git grep 'INSERT INTO chair_locations'`で1か所だけ）: `chairPostCoordinate` chair_handlers.go:117。同じtxで`INSERT … ON DUPLICATE KEY UPDATE`: 前回位置との`|Δlat|+|Δlon|`を足し、`total_distance_updated_at`は直後に読み戻す`location.CreatedAt`、`last_*`を今回の座標に。
- **初期化と再起動**: `webapp/sql/4-chair-distances.sql`（`DROP TABLE IF EXISTS` → `CREATE` → 初期データの`chair_locations`から窓関数で`INSERT … SELECT`）を`init.sh`の初期データ投入の後に1行足して流す。DBのテーブルなので再起動後もそのまま。起動時の作り直しは不要。
- **2台**: DBにあるので問題なし。同じ椅子の座標は前の成功を待ってから送られる（マニュアル「椅子」）ので、同じ行の並行更新は起きない想定（起きても行ロックで直列）。
- **猶予**: オーナーの移動距離合計は3秒の猶予がある（day.md「猶予時間」）が、同じtxで更新するので即時。

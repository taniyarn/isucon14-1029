# 設計: ライドの最新状態を`rides.status`列に持つ（`getLatestRideStatus`、report 20261029-135253）

決めてほしいこと: この形で実装してよいか（OKならレーン3が`impl/ride-status`で1本のPRに）。

- **何を**: `rides`に`status`列を足し、`ride_statuses`へのINSERTと同じtxで`UPDATE rides SET status = ?, updated_at = updated_at WHERE id = ?`。`getLatestRideStatus`の呼び元（8か所）は、もう読んでいる`ride`（`SELECT * FROM rides`）の`ride.Status`を使う。`ride_statuses`は通知の履歴として今のまま残す。
- **なぜ**: `getLatestRideStatus`がSQL時間の15%・62,916回（通知のポーリング2本とcoordinateから毎回）。列にすればこのクエリ自体が消える。
- **書き込み箇所**（`git grep 'INSERT INTO ride_statuses'`で6か所）: app_handlers.go:351（MATCHING、`appPostRides`）、:567（COMPLETED、評価）、chair_handlers.go:160（PICKUP）、:167（ARRIVED、どちらも`chairPostCoordinate`）、:325（ENROUTE）、:340（CARRYING、どちらも`chairPostRideStatus`）。全部の直後に上のUPDATEを足す。
- **落とし穴**: `rides.updated_at`は`ON UPDATE CURRENT_TIMESTAMP(6)`で、応答の`completed_at`・売上の期間・`ORDER BY updated_at`に使われている。状態の更新で動かさないよう`updated_at = updated_at`を必ず付ける。`Ride`構造体に`Status`を足す（JSONには出ない構造体）。
- **初期化と再起動**: `ALTER TABLE rides ADD COLUMN status …`と`ride_statuses`からのバックフィル（最新1行）を`init.sh`の初期データの後に流す（#22の`4-chair-distances.sql`と同じ型。`GROUP_CONCAT`は使わない）。DB列なので再起動・2台ともOK。
- **ロック**: `chairPostRideStatus`は既に`rides`を`FOR UPDATE`。`chairPostCoordinate`は新たに`rides`の行ロックを取るが、他のtxは`rides`→`ride_statuses`の順なので循環しない（推測。次のreportのErrors節で1213を見る）。
- **見込み**: SQL時間の15%と、通知1回あたりのクエリ1本が消える。

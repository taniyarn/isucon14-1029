## チーム合流の準備（人 #8）

### いつ合流するか（案）

| 合流点 | 条件 | 理由 |
|---|---|---|
| A: baseline の後 | `[DONE] servers`、baseline の run、kickoff ② が済んだ | チームが同じ report と app-map から始められる |
| B: 構成が決まった後 | DB 分離・DNS の置き場所・app ×2 の判断が済んだ（今回なら 01:19） | 構成を変える作業は 1 人で回す方が速い。以後は個別の改善なので分けやすい |

本番では **A で一度合流（状況の共有、10 分）→ 役割を分けて B まで並行**、を推奨。

### 合流時に渡すもの（ハブが作る）

`docs/journal.md` と panel の run から、1 枚にまとめる（`task` か skill にする）。

| 列 | 中身 |
|---|---|
| 変更 | PR 番号、1 行の中身 |
| 根拠 | report の行 / scan / deep-dive |
| 効果 | 前後の run のスコアと、効いた指標（例: search 142 → 21 ms） |
| 状態 | merged / revert / open（open は持ち主と残り） |
| 分かったこと | 律速の推移（DB → app CPU → 待ち → ベンチ機）、逆効果だったもの（TTL 60）、失格の芽（initialize 500） |

今回の分は `docs/journal.md`（00:40〜01:40）にある。表への変換はまだ。

### 合流後のタスク管理（GitHub Project）

- `task actions:issues` が report から issue を作る → Project の「Todo」に自動で入れる（Project の追加は `gh project item-add`）。
- 列: Todo / 担当中（人 or レーン）/ PR / merged / 効果判定済み。
- claims（`docs/claims.md`）と役割が重なるので、合流後は Project の「担当中」を claims の代わりにするか、両方を残すかを決める（未決）。
- レーンの `[PR]` と人の PR を同じ流れに載せる: レビュー todo（`PR=<n>`）を Project のカードからも開けるようにする（案）。

## 次の練習で確かめること

- ベンチのコマンドを起動の 1 行で渡し、初回ベンチまで 10 分以内に収まるか。
- 帯とロードマップのずれが起きる時刻と状態。
- 再起動試験（final-steps.md）を通す。
- ベンチ機を大きくしたときの頭打ちの位置。

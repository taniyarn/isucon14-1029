要点（先に結論）

  1. 去年は 35,076 点（実質 31〜35 位相当）を出しながら「データ保持NG」で失格。 今年の最優先は「失格しないこと」。最終1時間は改善を止め、自分たちで再起動試験と整合性チェックをやる。
  2. AI 利用がレギュレーションで明文化された初年度。 練習会（ISUNARABE 2026）の知見では、定型改善（N+1・index・設定）は AI が速いが、100万点級以降は「人間の仮説と計測」がないと伸びない。
    → 人間＝仮説・計測・判断、AI＝実装・検証・デプロイ の分業にする。
  3. 役割は「計測/インフラ係」「アプリ係×2」。 全員が Claude Code を1セッションずつ運転する。デプロイとベンチは1人（ベンチ番）が直列に捌く。AI はサーバーを直接触らず、必ずリポジトリ経由。
  4. 計測は pprotein（alp + slp + pprof）に一本化し、結果を Markdown に落として AI に読ませる。去年の otel/Jaeger は途中で剥がす羽目になったので今年は使わない。
  5. 手詰まり対策として、ベンチ単位でリソース時系列（sar + MySQL status + expvar）を CSV 保存し、アクセスログと 10 秒グリッドで突き合わせる「統合テーブル」と、DuckDB によるベンチのシナリオ復元（ユーザー増加曲線・遷移・ポーリング間隔）を用意する。 Prometheus / netdata は使わない。
  6. アプリ理解は「Playwright で収集 → Claude が app-map を書く」エージェントで 40 分以内に地図化する（§6.5、アイディア段階）。
  7. 開始直後の git 管理化と計測ツール導入は bootstrap.sh で自動化し、3 台 10 分以内で終える（§6.6）。去年はここに 40 分かかった。
  8. DB 分離などサーバー分割は 13:00 までに終える。 去年は 15:00 に着手して 20 分間 revert 合戦になった。
  9. お題は非公開。 作問は ISUCON14 準優勝チーム「第n西東京市」（初作問）。「AI に一発で解かれない問題」＝ドメイン理解とスコア式の読み解きが効く問題になる前提で準備する。
  10. 残り3週間で 素振りを2回（10/17 or 18、10/24 or 25）。1回目はツールと AI 運用の検証、2回目は本番リハーサル。

失格の直接原因は特定できていない。 ただし最終コミットでは setup() 内で db.Select に失敗すると panic する処理が追加されており、DB を別ホストに分離した構成では「再起動時に app が MySQL より先に起動して落ちる」リスクがある。再起動試験は「app が起動しているか」「ベンチ中に書いたデータが再起動後も残っているか」を見る。
→ 今年は (a) DB 接続は起動時にリトライ、(b) systemd は Restart=always、(c) 17:00 に全台 reboot → ベンチ → データ確認を自分たちでやる、を必須にする。

  • 悪かった: 計測基盤（otel）に時間を使って剥がした。サーバー分割が遅く、混乱した。SSE 化を最後まで着地できなかった。最終1時間まで変更を入れていた。再起動試験を自分たちで実施した痕跡がない。

3. 今年の基本方針

目標

  • 必達: 失格しない（再起動試験・データ整合性・レギュレーション遵守）
  • 目標: 有効スコアで上位 3%（去年なら 30 位以内）。スコアの絶対値は年ごとに違うので順位で考える

優先順位の原則

  1. 計測なしに改善しない。 alp / slp / pprof のどれかに根拠があるものだけやる（AI にも同じ制約を課す）
  2. 1 改善 = 1 ブランチ = 1 ベンチ。 効果が出なければ即 revert。「ついで」の変更を混ぜない
  3. 定型作業は AI、仮説と判断は人間。 「何を疑うか」を人間が文章にしてから AI に渡す
  4. お題の本質（スコア式・ドメインルール）を 11:00 までに全員が言語化する。 去年の上位はマッチングと通知間隔という「マニュアルにしか書いていない情報」で差がついた
  5. 壊しても戻せる状態を保つ。 設定ファイルも全てリポジトリ管理。サーバー上での手編集禁止

4. 3人でどう開発を進めるか

4.1 役割分担

A: インフラ・計測・ベンチ番

  • AMI 起動、初動スクリプト、リポジトリ化、pprotein 設置
  • nginx / MySQL / systemd の設定と サーバー分割
  • デプロイとベンチの実行権を一元管理（キュー管理、スコア記録）
  • 16:30 以降の安全化・再起動試験の責任者

B: アプリ①（読み系・DB）

  • マニュアルの「スコア」「制約」「許可されていること」を読み込んで要約
  • index、N+1、重いクエリ、キャッシュ
  • AI セッションで alp/slp 上位のエンドポイントを順番に潰す

C: アプリ②（書き系・ドメイン）

  • アプリを実際に触り、データモデルと状態遷移を把握
  • お題固有のロジック（去年のマッチング相当）、非同期化、外部 API
  • initialize の高速化、整合性が絡む変更のレビュー

※ 属人化を避けるため、サーバー分割の手順は事前に全員が一度やっておく（去年の参加記でも「担当外のメンバーがカバーできたこと」が勝因に挙げられている）。

4.2 Git / デプロイの運用

  • GitHub に当日用リポジトリを作成（/home/isucon 配下をまるごと管理。etc/ に nginx・mysql・systemd の設定も入れる）
  • main は常にデプロイ可能。短命ブランチ → 自分でマージ（レビュー待ちなし）。コンフリクトを避けるためファイル単位で担当を分ける（handler ファイルごとに持ち主を決める）
  • デプロイは task deploy BRANCH=xxx のみ。flock でロックし、同時デプロイを物理的に防ぐ
  • ベンチは A が回す。回す前に Discord に「bench: ブランチ名 / 何を見たいか」を書く。結果（スコア・fail 理由・alp 上位）を同じスレッドに貼る
  • サーバーの使い分け（3 台想定）: 午前中は svc1=ベンチ対象、svc2/svc3=各自の動作確認用。分割後は本番構成に統一

4.3 AI（Claude Code）の運用ルール

練習会の教訓: 「AI は疲れないが雑なミスをする」「複数エージェントが同時にデプロイ・ベンチすると競合する」「ISUCON 特有の割り切りを伝え続ける必要がある」。これを CLAUDE.md とスクリプトで強制する。
ルール理由・やり方
1 人 1 セッション、git worktree で分離同じ作業ツリーを複数 AI が触ると壊れる。git worktree add ../wt-feature をブランチごとに
AI はサーバーを直接編集しない許可するのは task deploy / task logs / 計測結果の読み取りのみ。ssh で設定ファイルを直接書く行為は hook で拒否
AI はベンチを回さないベンチは A が直列に実行。AI には「デプロイまで。ベンチは指示を待て」と書く
「設計だけ」「実装するな」を明示一発で大改修されるのを防ぐ。まず方針を出させ、人間が OK してから実装
ISUCON の前提を CLAUDE.md に書く互換性・保守性・テストは不要、API 仕様と静的ファイルは変更禁止、再起動後もデータは残ること、外部リソース禁止、複数台構成を前提にする（単一プロセス前提の mutex 等は要相談）
計測結果は Markdown で渡すmeasurements/<ts>/report.md（alp 上位 20・slp 上位 20・pprof top）を生成して読ませる。生ログは渡さない
変更の記録を残させるdocs/journal.md に「何を・なぜ・結果」を1行ずつ。別の人の AI が文脈を拾える
最終チェックは AI にもやらせる17:00 に diff 全体を「データ消失・再起動依存・外部通信」の観点でレビューさせる

5. どのように計測するか

5.1 計測スタック（去年の実績 + 上位チームの定番）

対象ツールメモ
HTTP（どの API が重いか）alp（nginx ltsv ログ）sum でソート。alp.yml の matching_groups は当日 AI に生成させる
SQLslp または pt-query-digest（slow log, long_query_time=0）ベンチ中だけ ON。最終ベンチでは必ず OFF
Go アプリ内部pprof / fgprof（net/http/pprof を :6060 に）CPU だけでなく alloc も見る。JSON マーシャルや正規表現が上位に来がち
上記のまとめpprotein（別 EC2 で稼働、各サーバーに pprotein-agent）initialize のタイミングで自動 collect。ログローテートも面倒を見てくれる。複数台でも agent を置けば OK
リソースtop / dstat / netdata、SHOW PROCESSLIST、SHOW ENGINE INNODB STATUSCPU が張り付いているのが app か DB か、ロック待ちか、を 1 分で判断する用
ベンチ結果ポータルの fail 理由・エラー件数スコアと同じくらい「エラーで減点されていないか」を見る
去年の otel + Jaeger は、導入に 15 分、剥がすのに 10 分かかって本番では使えなかった。今年は pprotein 一本。トレースが欲しくなったら pprof とログで代替する。

5.2 計測ループ（1 サイクル 10〜15 分を目標）

1. task deploy BRANCH=xxx        # flock 付き。nginx/mysql 設定も同時に反映、ログをローテート
2. ベンチ番がポータルでベンチ実行   # initialize の hook で pprotein の collect と各サーバーのサンプラー（§5.5）が同時に開始
3. task measure:collect            # 各サーバーから access.log / slow.log / sar / mysql_status / expvar の CSV を回収
4. task report                     # alp 上位20 / slp 上位20 / pprof top30 / 統合テーブル を measurements/<ts>/report.md に出力
5. task log:scenario               # DuckDB でユーザー増加曲線・遷移・シンクタイムを出力（§5.6。初回と大きな変更後は必ず見る）
6. Discord にスコア + report の要約を投稿
7. 各自の AI セッションに report.md を読ませて次の仮説へ

5.3 「何を見るか」のチェックリスト

  • alp: sum 上位 5 エンドポイントで全体の何 % を占めるか。count が異常に多い API（ポーリング系）はないか
  • slp: 同じクエリが count 万単位で出ていないか（N+1）。EXPLAIN で type=ALL が残っていないか
  • pprof: runtime.mallocgc / json / regexp / sort が上位なら、アプリ側のアルゴリズムやキャッシュの出番
  • DB の CPU と app の CPU、どちらが 100% か。両方余っているならロック待ち or 外部 API 待ち or ベンチ側の制約（ポーリング間隔など）
  • ベンチの fail/エラー: 整合性エラーが出ていたら、スコアが伸びても放置しない

5.4 手詰まりになった時に見るもの

alp / slp / pprof は「一番重いもの」を見つける道具なので、上位を潰し切ると平らになる。その時点でボトルネックは次の 3 つのどれかに移っている。

  1. どのサーバーも CPU が余っている: スループットではなく「待ち」が律速（ロック待ち、コネクションプール待ち、外部 API 待ち、ポーリング間隔、ベンチ側のシナリオ制約）。去年のマッチング（500ms に 1 件）はこれ
  2. プロファイルに出ない資源が飽和: DB のロック、fsync、サーバー間ネットワーク帯域、ephemeral port、fd、GC
  3. ベンチの挙動がスコアを決めている: 遅延がある閾値を超えるとユーザーが増えない、エラーで減点、特定イベント完了数でしかスコアが伸びない
症状見るもの道具
app の CPU が 100%CPU だけでなく alloc と GC、goroutine 数pprof の alloc / goroutine、GODEBUG=gctrace=1
DB の CPU が 100% で slp 上位は潰した「軽いが回数が多い」クエリの往復回数、Questions/sec、Threads_runningSHOW GLOBAL STATUS の差分、sys.statement_analysis
どこも CPU が余っているロック待ちとプール待ちsys.innodb_lock_waits、Innodb_row_lock_time、Go の db.Stats().WaitCount / WaitDuration、pprof の block / mutex
同上、ロックでもない外部 API のレイテンシ、ポーリング間隔、マニュアルの「待ち」の記述alp を sum ではなく p99 でソート、外部呼び出しの所要時間ログ
スコアが途中から伸びないベンチの負荷曲線。何秒目にユーザーが増えなくなるか、その直前に何が起きたか§5.6 のユーザー増加曲線と統合テーブル
ベンチ結果にエラーや timeout4xx / 5xx の内訳と本文、整合性エラーの原因status 別集計、app のエラーログ、§5.6 の「エラーの文脈」
複数台化したのに伸びない止め忘れた常駐プロセス、片寄ったトラフィック、サーバー間帯域ps、ss -s、§5.5 の NIC 系列
一番効くのは「仮説を数値にする」こと。 プロファイラを眺めるより、(1) スコア式に直結する業務イベント（例: 作成 → マッチ → 完了）の件数と所要時間を毎秒カウンタで出す、(2) マニュアルから「遅延ゼロならスコアはいくつか」を概算し、今のスコアとの差＝待ちの総量と捉える、の 2 つをやる。練習会上位の「仮説 → カウンタを 1 行足す → 数値で確認 → 別原因が判明」という流れを真似る。

5.6 ユーザー行動（ベンチのシナリオ）の深掘り

ベンチがアプリをどう使うかはスコアの天井を決める最重要情報。初回ベンチが一番の宝（サーバーが遅い状態ではベンチの「待ち方」が露骨に見える）。baseline のログは別名で必ず保存する。

nginx のログ項目を足す

log_format ltsv "time:$msec"
    "\tmethod:$request_method\turi:$request_uri\tstatus:$status"
    "\treqtime:$request_time\tapptime:$upstream_response_time"
    "\tsize:$body_bytes_sent\treqsize:$request_length"
    "\tsess:$cookie_app_session"        # Bearer 方式なら $http_authorization
    "\tua:$http_user_agent\tconn:$connection\tconnreq:$connection_requests"
    "\tupstream:$upstream_addr";

cookie 名は当日のアプリに合わせて変える。$msec が入っていないと秒未満の時系列が作れない。

分析は DuckDB で

単一バイナリで ltsv / CSV を読め、ウィンドウ関数が使え、AI が SQL を書くのも得意。task log:import で access.parquet に変換し、クエリ集を sql/ に置いておく。

観点取り方分かること
ユーザー増加曲線10 秒ごとのユニーク sess 数何秒目で増えなくなったか＝スコアの天井。改善前後で比較
シナリオの復元セッションごとにエンドポイント列を並べ、遷移行列（A の次に B が来る確率）ループしている区間がポーリング、分岐が少ない区間が 1 本道のシナリオ
シンクタイム / ポーリング間隔同一セッションの連続リクエストで「前のレスポンス完了 → 次のリクエスト」の間隔ほぼ 0 なら遅延がスコアに直結。固定値ならベンチの sleep で、速くしても意味がない（去年の 30ms ポーリングはここで見えたはず）
シナリオ完了数の時系列スコアに直結するエンドポイント（去年なら evaluation の POST）を 10 秒ごとに数えるスコアの代理指標。ベンチ結果を待たずに改善の効きを判断できる
エラーの文脈4xx / 5xx の直前にそのセッションが何をしていたか整合性エラーの再現手順
役割の分離UA や URI プレフィックスで一般ユーザー / 管理者 / bot を分け、それぞれの増加曲線どの役割がボトルネックで止まっているか
検索条件の分布$request_uri のクエリ文字列を集計index 設計の根拠（どのフィルタ組み合わせが多いか）
接続の使われ方conn / connreq の分布keepalive が効いているか、同時接続数の上限に当たっていないか
-- 10秒ごとのユニークセッション数と req/s
SELECT floor(time/10)*10 AS t, count(*)/10.0 AS rps, count(DISTINCT sess) AS users
FROM access GROUP BY 1 ORDER BY 1;

-- セッション内の遷移（前のリクエスト → 次のリクエスト）と間隔
WITH s AS (
  SELECT sess, uri_group, time,
         lag(uri_group) OVER w AS prev,
         time - lag(time + reqtime) OVER w AS gap_sec
  FROM access WINDOW w AS (PARTITION BY sess ORDER BY time)
)
SELECT prev, uri_group, count(*), median(gap_sec), quantile(gap_sec, 0.9)
FROM s GROUP BY 1,2 ORDER BY 3 DESC LIMIT 30;
この分析は AI の得意分野。「この遷移表からベンチのシナリオを推定し、マニュアルの記述と突き合わせて」と投げると仮説がすぐ出る。最終ベンチ以外はログを常に ON にし、全ベンチの measurements を残す。

6.5 アプリ理解を加速する「アプリ分析エージェント」（アイディア）

目的: 競技開始から 40 分以内に「画面 → API → ハンドラ → テーブル」の地図（app-map）を作り、全員と AI が同じ理解で動き出すこと。去年はマニュアル読みとアプリ触りに 1 時間かけていた工程を、収集を自動化して考察に時間を使えるようにする。

基本構成: 収集はスクリプト、考察は Claude

層やること
① 収集（Playwright スクリプト）決定的・網羅的に画面を巡回してリクエストを全部記録する。人が見ても AI が読んでも同じ結果になる
② 対話的な補完（Playwright MCP）「配車を依頼して完了まで進める」のようにボタン操作が要る導線は、Claude Code の Playwright MCP で Claude 自身に操作させ、browser_network_requests で通信を回収する
③ 考察（Claude）①②の結果 + Go のルーティング + スキーマ + マニュアルを読んで docs/app-map.md を書く

① 収集スクリプトの仕様案（crawl → report）

  • ペルソナ（guest / user / owner / admin …）ごとにブラウザコンテキストを分け、Cookie 注入でログイン状態を作る（ISUCON のアプリはセッショントークンを Cookie に入れる方式が多い。去年は app_session / owner_session）。トークンは初期データや DB から拾う
  • 設定ファイルに seed URL（フロントの README やルート定義から転記）を書き、ページ内の同一オリジンリンクを BFS で辿る（上限 40 画面程度）
  • 各画面で 数秒滞在し、XHR / fetch / SSE / WebSocket をすべて記録。method、path（ID は :id に正規化）、query、status、所要 ms、リクエスト body、レスポンス JSON のサンプル（先頭 800 文字）
  • 同じエンドポイントが繰り返し呼ばれていたらポーリングとして間隔の中央値を出す。SSE は接続として記録
  • 画面ごとにスクリーンショット、title、見出し、フォーム（method / action / 入力項目）、ボタン文言、リンク一覧
  • JS バンドルの静的走査: /api/ で始まる文字列、setInterval の数と間隔リテラル、EventSource / WebSocket の有無を抽出。「コードにはあるが巡回では観測できなかった API」を一覧にして、見落とした導線を示す
  • flows: 任意のスクリプト（「登録 → ログイン → 投稿」など）を差し込めるフックを用意し、その間の通信を "flow:名前" として同様に記録
  • 出力は report.md（AI 用。画面一覧、画面ごとのリクエスト、エンドポイント集計、ポーリング、未観測 API）と report.html（人間用。スクショ付きカード + 表）

③ Claude に書かせる app-map.md の中身

  • 画面一覧と役割（誰が使う画面か、何を見ているか）
  • エンドポイント表: method / path → Go ハンドラ関数 → 触るテーブル → 呼び元画面 → 観測された頻度（ここが本体。alp の結果をこの表に貼れば「どの画面が重いか」が即分かる）
  • データモデルと状態遷移（エンティティの状態と、それを進めるエンドポイント）
  • スコア式・ユーザー増加条件に関係する導線の仮説（マニュアルの記述と突き合わせ）
  • ポーリング・SSE・外部 API・非同期処理など「待ち」が発生する箇所
  • 疑わしいホットスポット（N+1 になりそうな一覧系、集計系、全件走査）と、確認すべき計測
  • 分からないこと・マニュアルで確認すべきことのリスト
注意: ベンチマーカーはブラウザを使わない。 API を直接叩くので、この分析で分かるのは「ドメインと画面 ↔ API の対応」であって「ベンチの行動」ではない。ベンチの実際の挙動は §5.6 のアクセスログ分析で見る。両方揃うと「この API はベンチが何のシナリオで叩いているか」が分かる。

pprotein-agent の常駐可systemd unit を置いて enable。pprotein 本体の計測サーバーは前日に立てておく（モニタリング用の外部サーバーはレギュレーション上 OK）
リソースサンプラー（§5.5）可スクリプトと unit を配置。起動は initialize hook から
動作確認可最後にまとめて表示: ltsv でログが出ているか、スローログが生成されるか、curl :6060/debug/pprof/ が返るか、agent が計測サーバーと疎通しているか

自動化できない部分は「検出して渡す」

アプリ固有の値（DB 名、systemd のサービス名、nginx のサイトファイル名、アプリのポート、ログイン方式）はスクリプトが推測して server-info.md に書き出し、Claude に「この情報から Taskfile の変数と alp の matching_groups を埋めて」と投げる。人間はその間マニュアルを読む。

事前にやること

  • 素振りで ISUCON13 と 14 の AMI 両方に bootstrap.sh を通す。Ubuntu のバージョン、MySQL の設定ディレクトリ、nginx のレイアウトが回ごとに違うので、壊れる箇所をここで潰す
  • 3 台並列実行（task setup:all）と、svc2 / svc3 の repo 取り込みが正しく動くことを確認
  • pprotein の計測サーバーを前日に立てる手順（docker compose）を用意
  • server-info.md から Taskfile の変数を埋めるプロンプトを skill にしておく

8.2 失格を避ける最終チェックリスト（16:30〜）

  • アクセスログ・スローログ・pprof・デバッグログを OFF にしてデプロイ
  • 全サービスが systemctl is-enabled になっている（app、nginx、mysql、ワーカー類。分割後に止めたものは disable）
  • app は DB に接続できるまでリトライする。After=mysql.service と Restart=always
  • インメモリに持っているデータは再起動で復元できる（DB に書いている / 起動時にロードする）
  • 全台 reboot → ベンチ完走 → ベンチ中に作られたデータが残っているか確認 → もう一度ベンチ
  • ベンチ中に外部リソース（計測サーバー含む）へ処理を委譲していない。pprotein-agent は残っていても OK だが、アプリから外部へ同期的に通信していない
  • API の URI・レスポンス構造・静的ファイルを変えていない（AI の diff レビューで確認）
  • 最終構成（各サーバーの役割）を記録。18:00 以降サーバーを触らない

8.3 コミュニケーション

  • Discord 音声は常時接続。会話は「今やっていること」「ベンチ回す／回した」「困っている」の 3 種類に絞る
  • スコア推移と施策一覧は管制盤の Score timeline に集約する（run ごとに commit・診断・5xx が自動で付く。人が入れるのはスコアとメモだけ）。「今の main のスコア」「どの変更で上がった／下がった」が常に分かる状態にする
  • 1 時間ごとに 5 分 sync。詰まっている人がいたら担当替え

8.3b 終了後の振り返り（練習ごとにやる）

  • 素材は自動で溜まる: run ごとの meta.json（デプロイ commit、req、5xx、所要時間）と summary.md（当時の診断と next actions）、管制盤で入れたスコア・メモ・ベンチ出力。生ログを消しても残る
  • task retro REPO_DIR=<contest repo> で手元に retro.md / retro.html を生成する。中身: スコア × 時刻 × commit の時系列、run 間に入った commit 一覧、診断（verdict）の推移、主要エンドポイントのレイテンシ推移、ベンチ出力、issue 一覧（ISSUES=1）
  • Claude に retrospective skill（tools/isumeasure/retrospective/SKILL.md）で振り返り文書を書かせる。形式は固定: 結果 → スコア推移 → 効いた手・効かなかった手（Δスコアと verdict の遷移を根拠に） → 時間の使い方（セットアップ / 把握 / 改善 / 終盤、手が止まった区間） → 問題 → 来年のチェックリスト。80 行以内
  • 振り返りの質はメモの質で決まる。ベンチを回した人は その場で 管制盤の note に「何を変えたか」を 1 行入れる（commit メッセージが代わりになるので、コミット単位でデプロイしていれば空でも良い）

8.5 AI 利用で特に気をつけること

  • AI は「堅実すぎる提案」をしがち（練習会の複数記事で指摘）。インメモリ化や大胆な構成変更は人間が決めて指示する
  • 「単一サーバー前提の最適化（プロセス内 mutex 等）」は複数台化で壊れる。CLAUDE.md に「最終構成は app 複数台の可能性がある」と書く
  • AI の実装は速いのでベンチ待ちが律速になる。各自のサーバーで簡易負荷（curl / リプレイ）をかけて、ベンチ前に明らかな fail を潰す
  • レギュレーション上、AI は開発補助として OK。ただし競技時間中に「問題について外部の人と話す」のは禁止なので、公開のチャットや SNS に問題内容を貼らない

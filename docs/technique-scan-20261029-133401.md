## 決めてほしいこと（U1〜U3。全部OKなら何もしなくてよい）

### U1 マッチングを「待ち全件 × 空き椅子全件、到着が早い順」に作り直す（担当: レーンc、T34）
- 変わること: `internal_handlers.go` の `internalGetMatching` だけ。1回の呼び出しで1件（ランダムな椅子を最大10回試す）→ 待っているride全件を、空き椅子の中から「乗車位置までのマンハッタン距離 ÷ モデルの速度」が最小の椅子に古い順に割り当てる。応答は204のまま、他のファイルに触らない。約80行（ルール6の50行超なので、このOKを設計のOKとする。設計は付録A）
- 見込み: ベンチの不満は「100%のライドがマッチまでの時間、88.9%が迎車距離」（bench.log）。評価が上がるとユーザーが増える（app.md「ライド」）→ 完了ライド数が増える（推測。14 matsuu 6,025 → 21,023、都営三田線 11,068 → 21,372）
- リスク: 「空き」の判定を参考実装と同じ「COMPLETEDの通知を椅子が受け取り済み」にする（椅子が完了通知の前に次のライドを受けるとクリティカル）。matcherは#4でsvc1の1本だけ。猶予・再起動には触らない

### U2 matcherの間隔 500 ms → 100 ms、nginx/TLSを通さず app に直接（担当: レーンc、T35）
- 変わること: `etc/systemd/system/isuride-matcher.service.d/interval.conf`（新規、`ExecStart=` を `curl -s http://127.0.0.1:8080/api/internal/matching; sleep 0.1` に）+ `deploy.sh` の0節の末尾に etc_install と svc1 だけ restart の3行。`env.sh` は触らない
- 見込み: baselineではsvc1のmatcherの実際の間隔が中央値1,182 ms（p90 1,399 ms。設定は500 ms、svc2/3は535 ms）= 負荷の掛かったnginx+TLS経由のcurlが1回600 ms余計に掛かっていた（summary.md「Periodic internal endpoints」）。待ち時間の上限が1.2秒 → 0.1秒。U1と組で「マッチまでの時間」の不満を消しにいく
- リスク: app.md「ライドのマッチング」が間隔も仕様も自由と明記。1回の呼び出しは待ちが無ければ1 ms（svc2/3の実測）。再起動後はunitのdrop-inとenableがそのまま残る。他ホストでは#4の `disable --now` のまま（restartはsvc1だけに限定）

### U3 決済の冪等化: `Idempotency-Key: <ride id>` を付け、決済HTTPをクライアント切断に巻き込まれないようにする（担当: レーンc、T14 + T39、守り）
- 変わること: `payment_gateway.go` の `requestPaymentGatewayPostPayment`（ヘッダ1行、ctxを `context.WithoutCancel`、失敗時の再送はGET /paymentsの件数比較をやめてそのまま再送）+ `app_handlers.go` の `appPostRideEvaluatation` の呼び出し1行（ride idを渡す）。応答の形は同じ
- 見込み: スコアには直結しない（評価は9回/60秒、5xx 0）。本番の決済サーバーは「混むとエラー」（app.md「決済マイクロサービス」）で、今の実装は失敗のたびに GET /payments + 100 ms × 最大5回。評価のレイテンシが減る（推測）
- リスク: 今の実装は評価のtxの中で外部HTTPを呼び、`r.Context()` を使う。評価リクエストがベンチ側で切られる（baselineでも499と「context canceled」×18）と「決済は通ったがtxはロールバック」→ 次の評価でもう一度請求 →「決済サーバーに誤った支払い」のクリティカル（FAIL）の芽。openapi.yamlは `Idempotency-Key` を受け付ける（`webapp/payment_mock/openapi.yaml` の POST /payments）。レーン3の `integ/20261029-133401` は `appPostRideEvaluatation` に触らない（claims確認済み）

## 付録A: U1 matching の設計（15行）

1. 待ち: `SELECT * FROM rides WHERE chair_id IS NULL ORDER BY created_at`（index `rides(chair_id, updated_at)` 済み #6）。0件なら204。
2. 空き椅子: `chairs c JOIN chair_models m ON m.name = c.model`、`c.is_active = TRUE`、かつ `NOT EXISTS (rides r WHERE r.chair_id = c.id AND NOT EXISTS (ride_statuses rs WHERE rs.ride_id = r.id AND rs.status = 'COMPLETED' AND rs.chair_sent_at IS NOT NULL))`（= 全ライドで COMPLETED を椅子が受信済み。参考実装の `COUNT(chair_sent_at) = 6` と同値: 遷移は順に挿入・順に送信される）。
3. 各空き椅子の最新位置: `chair_locations WHERE chair_id = ? ORDER BY created_at DESC LIMIT 1`（index済み。520椅子なら数ms。位置が無い椅子は候補から外す = 参考実装でも `nearby` に出ない）。
4. 割り当て: ride を古い順に、候補の中で `(|lat差| + |lon差|) / speed` 最小の椅子を選び、`UPDATE rides SET chair_id = ? WHERE id = ? AND chair_id IS NULL`、その椅子を候補から外す。候補が尽きたら残りは次回。
5. 距離の上限は付けない（「長時間マッチングされない」はクリティカル。遠くても割り当てる）。
6. tx無し（参考実装と同じ。matcherは1本）。2台構成でも `/api/internal/` はsvc1のnginxのlocationで svc1 の app に固定（#4のレビューで確認）。
7. 再起動: 状態はDBだけ。`/initialize` に触らない。
8. 計測: 次のrunの bench.log の不満の内訳（マッチ待ち / 迎車）と「Periodic internal endpoints」の avg ms。

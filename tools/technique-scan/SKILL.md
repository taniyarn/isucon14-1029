# technique-scan

## いつ使うか

2〜3 回目のベンチの後、`parallel-fix` の 1 周目が終わって「次に何をやるか」が report の Next actions だけでは尽きかけた頃（12:30 頃）。**レーン c（スカウト、`docs/lanes/c-scout.md`）が回す**。きっかけはレーン 1 の `[PHASE] loop technique-scan TS=<ts>`。始めと終わりに `task lane:status LANE=c …`、終わったら `[DONE] c technique-scan docs/plans/<ts>-techniques.md` をレーン 1 へ（作業単位はレーン 1 が `[TASK] 2 fix PLAN=…` で配る）。1 枚で回すときは人が:

```
technique-scan skill で。対象 run は <ts>
```

目的は「過去のコンテストで効いた手を、この問題に対して **漏れなく** 当てはめて可否を決める」こと。思いつきで 2〜3 個試すのではなく、カタログ全件に ○ / × / 要確認 を付ける。

早期モード（run 無し）は下の「早期モード」節。レーン c が `[TASK] c early-scan`（baseline の前後）で 1 回だけ回す。中盤の 12:30 の scan はそのまま残す（早期モードの「要確認（計測待ち）」をここで ○ / × に決める）。

## 入力（全部 repo にある。無ければその旨を書いて進める）

| 入力 | 何を見るか |
|---|---|
| `docs/TECHNIQUES.md` | カタログ本体。各テクニックの「効く条件」「当日の確かめ方」「リスク」 |
| `docs/manual/*.md` | レギュレーションとアプリケーションマニュアル。許可・禁止・整合性の猶予（「N 秒以内に反映」等）・スコア式・外部通信・再起動後の要件 |
| `docs/kickoff.md` | 構成要素、禁止事項の要約、スコア式 |
| `docs/app-map.md` | 画面 → API → ハンドラ → テーブル、書き込み経路、Data model（ER、行数） |
| `measurements/<ts>/summary.md`（`task run:pull TS=`） | Where the time goes、endpoint 表（304% 列、count）、SQL 表（code 列 = SQL を発行した行）、**Data growth 表**（ベンチ中に増えないテーブル = Δ 0）、Bench shape、**Flows**（Score loops = 点を生むループと各ステップの応答時間 → T32、Drop-off = 4xx/5xx や遅さで離脱したクライアント → T33）、Unmatched paths |
| `webapp/sql/*.sql`、`webapp/go/*.go` | スキーマ、ハンドラの実装（キャッシュ可否は書き込み経路で決まる） |

## 手順

1. マニュアルから **制約の表** を先に作る: 変更してよいもの / だめなもの、ステータスコードやヘッダの扱い、整合性の猶予（秒数つき）、再起動後に残すべきデータ、外部通信、静的ファイル。各行に出典（ファイル名と見出し）。
2. `summary.md` の Data growth 表から **増えないテーブル**（Δ = 0）と **追記だけのテーブル**（INSERT のみ、UPDATE/DELETE 無し。app-map の書き込み経路で確認）を列挙する。
3. endpoint 表の上位 20 件について、**同じ応答が続く条件**を調べる: パラメータの種類数（Unmatched paths や access.csv の distinct）、応答が依存するテーブル、更新頻度。
4. `docs/TECHNIQUES.md` の **全テクニック（T1〜T41）** を番号順に判定する。1 つも飛ばさない。§7 の「守り」表は判定ではなく、○ にした手ごとに該当する落とし穴を「リスク」欄に転記する。判定は 3 値:
   - ○ 使える: 効く条件が 2 と 3 の事実で満たされ、1 の制約に触れない。期待効果（endpoint の share %、SQL 時間の %）を数字で。
   - × 使えない: 条件が満たされない、または制約に触れる。理由を 1 行。
   - 要確認: 条件は満たすが、マニュアルの解釈や整合性の猶予が曖昧。**人に聞く質問を 1 行**で書く。
5. ○ と要確認を **期待効果 × 実装コスト** で並べ、上位を `parallel-fix` の作業単位（ファイル単位、index 群、ops 群）に落とす。`docs/plans/<ts>-techniques.md` に書く。
6. 出力を `docs/technique-scan-<ts>.md` に保存し、要点（○ の件数、上位 5 件、人に聞く質問）を 10 行にまとめて返す。人に聞く質問は 1 つずつ `task lane:todo LANE=c MSG="<質問と選択肢>" WHY="<T#>の可否" AFTER="答えをレーン c のタブに"`（文章だけで聞かない）。

## 出力の形

```
# technique-scan <ts>

## 制約（マニュアルから）
| 項目 | 可否 | 出典 |

## 事実（run <ts>）
- 増えないテーブル: …（Data growth Δ=0）
- 追記だけのテーブル: …
- 上位 endpoint と依存テーブル: …

## 判定（TECHNIQUES.md の順。全件）
| T# | テクニック | 判定 | 根拠（事実 / 制約の出典） | 期待効果 | コスト | 作業単位 | 守り（§7 の該当行） |

## 人に聞くこと
1. …

## 次の parallel-fix に渡す作業単位
```

## 早期モード（run 無し、10:15 頃）

指示（レーン c が `[TASK] c early-scan` で。kickoff phase 1 の commit の後、origin/main に `webapp/` が来ていること。main の checkout では pull せず worktree で読む。始めと終わりに `task lane:status LANE=c …`）:

```
technique-scan skill を早期モードで（run 無し）
```

入力は `docs/manual/*.md`、`docs/kickoff.md`（phase 2 の「先読みの手」があれば。無ければ自分で同じ grep をする）、`docs/FIRST-HOUR.md`（型ごとの候補）、`webapp/sql/*.sql`、`webapp/go/*.go`（grep で当たった所だけ）。`summary.md` と app-map は無い前提。

手順の違い:

1. 手順 1（制約の表）は同じ。
2. 手順 2・3（Data growth、endpoint 表）は飛ばす。代わりに `docs/FIRST-HOUR.md` の型を選び、その grep をマニュアルとコードに当てる。
3. 判定は全件（T1〜T41）。ただし:
   - **○ にしてよいのは、効く条件がマニュアルの文とコードだけで満たされる手**（例: T17 = マニュアルに「`retry_after_ms` を待つ」+ コードの定数が 30 ms、T34 = 「自由に変更可」+ `ORDER BY RAND()`、T37 = initialize のパラメータ、T35 = 固定間隔の定数）。根拠は「マニュアルの見出し + file:line」。
   - **効くかどうかが計測で決まる手**（T1 の増えないテーブル、T2 / T6 の回数、T8 の増え方、T20 / T21 の SQL の重さ、T24〜T31 の構成と設定）は、条件がコードで見えていても **要確認（計測待ち）** にする。質問ではなく「baseline の summary.md の <表> を見る」と書く。
   - 期待効果は数字で言えない。「1 回 1 件 → 全件」「30 ms → N ms でリクエスト数 1/k（推測）」のように、コードから言えることだけ書き、残りは「推測」。
4. ○ のうち **整合性の猶予に触らない手**（または、マニュアルの秒数の内に収まると書ける定数だけの手）を作業単位にする（最大 3 つ、`U1`〜`U3`）。**ハンドラのファイルに触る手はレーン 3 の early-fix に回す**（レーン c は設計と根拠だけ。2026-10-27 夜: c の retry_after と matching がレーン 3 の claims とぶつかった）。レーン c が自分で実装するのは、レーン 3 が触らないファイル（決済の client、ワーカー、`etc/` 以外の付随の設定など）の手だけ。index と N+1 はレーン 3。
5. 出力は `docs/technique-scan-early.md`。**人がまず読むのは先頭だけ**なので、次の順に書く（2026-10-27 夜: 決めてほしいことが一番下で、6 列の表に詰め込まれていて読めなかった）:
   ```
   # technique-scan early（<日付>）
   ## 決めてほしいこと（U1〜U3、全部 OK なら何もしなくてよい）
   ### U1 retry_after_ms 30 ms → 500 ms（担当: レーン 3）
   - 変わること: app と chair の通知 4 か所の定数だけ（`app_handlers.go:676` など）。応答の形は同じ
   - 見込み: 通知のリクエスト数がおよそ 1/10（推測）。通知は時間の 66%
   - リスク: マニュアルの「3 秒以内」の内。なし
   ### U2 …
   ## 人に聞くこと（あれば 1 問ずつ: 問い / 選択肢 / 推奨と理由）
   ## 付録: 制約（マニュアル）/ コードの兆候（file:line）/ やらないこと
   ```
   1 単位は 3 行（**変わること**は「何が → 何に」と触る場所、**見込み**は数字 1 つか「推測」、**リスク**は猶予・再起動・2 台）。根拠の表は付録に。main への commit はしない（ブランチ `scan/early` で push して、パスを返す）。Discord 用の 10 行は「レーン c でやる手 / 要確認（計測待ち）の数 / 人に聞くこと」。
6. scan の文書を docs だけの PR（`[fast]`）で push してから、レーン 1 に `[PICK] #<PR> units=<n> ask=<n>`（docs/MESSAGES.md）を送る。ハブは作業単位を **`PICKS="U1 …::…|U2 …::…"` の todo 1 つ**（盤に単位ごとのトグル。人は外したいものだけ外して「✅ 選んだものを OK」）にし、人への質問は 1 問 1 つの `CHOICES` の todo にする。`[DECIDED] picked=U1 U3` で来た単位だけを実装する（ハンドラの単位はレーン 3 へ）。

## ルール

- 判定の根拠は必ず **この run の数字か、マニュアルの該当箇所** を引く（早期モードはマニュアルの該当箇所とコードの file:line）。「一般に効く」は根拠にならない。
- ベンチの挙動についての記述は **推測** と明記する（deep-dive の §10 と同じ扱い）。
- 整合性の猶予（「N 秒」）はマニュアルの数字をそのまま書き、無ければ「猶予の記載なし → 要確認」にする。
- 再起動試験（IMPLEMENTATION-NOTES §0）に触れる手（メモリだけに持つ書き込み、ローカルファイル）は、永続化の方法を書けない限り ○ にしない。
- `summary.md` と `docs/` 以外の生ログは読まない（必要なら deep-dive skill）。
